# Pruebas

**Criterio:** cada prueba fija un comportamiento que un evaluador podría verificar a mano, o una propiedad que un error real rompería. Nada se escribe para subir cobertura.

```bash
pnpm test           # todo; necesita un Postgres (TEST_PG_URL)
pnpm test:unit      # solo las unitarias, sin base
```

El CI (`.github/workflows/ci.yml`) corre `typecheck`, `test:unit` y `test:db` en cada PR contra un Postgres 18 de servicio, y después `docker build .` desde el checkout limpio.

Las pruebas con base crean su propia base de datos `cocos_test` desde cero, con **el mismo bootstrap que producción** (seed del challenge, migraciones, funciones). Cada prueba usa usuarios nuevos: las órdenes no se pueden borrar, así que nadie hereda estado de otra prueba. Por defecto `TEST_PG_URL=postgresql://postgres:postgres@localhost:5432/postgres`, que es el Postgres de `docker compose up`.

La línea que tenía el README se detecta; una descripción de las suites o los parámetros de la prueba de propiedad, no. Dos ramas que agregan cada una un archivo de test y su fila en esta tabla (y actualizan cualquier cuenta que quede en un `.md`) se fusionan sin conflicto con `git merge-tree`, en un repositorio temporal con los `.md` actuales; control: con una cuenta en el README, chocan en esa línea. |
| `test/unit/commit-msg` | Formato obligatorio de commits y PRs ([`CONTRIBUTING.md`](../CONTRIBUTING.md)): el mensaje completo pasa; cada sección faltante, vacía o fuera de orden, tipo inválido, título largo o con punto, `Refs` sin issue y texto libre al final fallan con un mensaje que dice qué corregir. La CLI `check.ts` en sus tres modos: `--file`, `--range` (un commit inválido entre válidos y un merge fallan) y `--pr`. |
| `test/unit/codex-review` | `scripts/codex-review.sh` contra un repositorio de prueba con `gh` y `codex` simulados: qué publica con cada veredicto (review sobre el commit, un hilo por hallazgo, `codex/review`), que Codex corre en solo lectura y con el schema de la salida, que el prompt, las reglas y el schema salen de la rama base aunque el PR los cambie, que `--dry-run` no escribe nada, que `ci` o `commit-messages` ausentes, omitidos o pendientes frenan antes de Codex, que un bloqueante anterior sin disposición (aunque su hilo se haya cerrado a mano) impide aprobar, qué hilo se resuelve y cuál se reabre, que las respuestas en los hilos (reviews con el cuerpo vacío) no cuentan como corrida ni cortan la segunda, cada control de coherencia de la salida de Codex y el límite de iteraciones. `--after-rebase`: con la última corrida aprobada, un rebase que solo cambia documentación (o nada) deja `codex/review` en verde citando el review aprobado, comenta la comparación y no corre Codex ni publica una corrida; un cambio de código (una línea, un espacio, `docs/process/`, un `.md` en `src/`, el mismo cambio movido a otra función o método con el mismo cuerpo, también en PL/pgSQL, un archivo del PR que la base también cambió, aunque el rebase lo deje igual al aprobado, o un archivo que solo cambia de modo) corre Codex aunque ya haya 4 corridas, y esa corrida no cuenta para la siguiente; sin corrida aprobada, o si una corrida ya revisó el commit, se rechaza sin escribir; un review de otra cuenta, con la marca citada o con un sha distinto de su `commit_id` no es una aprobación; repetirlo sobre el mismo rebase, también después de revisar otro commit, no vuelve a correr Codex ni duplica el comentario. |
| `test/unit/package-manager` | Solo pnpm ([#6](https://github.com/dante0x95/cocos-challenge/issues/6)): `pnpm-lock.yaml` es el único lockfile versionado (ni `package-lock.json` ni `pnpm-lock.yaml.bak`); `.gitignore` ignora `package-lock.json` y cualquier `.bak` pero no `pnpm-lock.yaml`; `packageManager` de `package.json` es el mismo `pnpm@x.y.z` que instala el `Dockerfile`. |
| `test/unit/orders` | Forma del `POST /orders` (escala, floats, campos de más, combinaciones), hash de idempotencia independiente del orden de las claves y de la escala de `amount`/`price` (`100`, `"100"`, `"100.0"`, `"100.00"`, `" 100.00 "` dan el mismo; `"100.001"` se sigue rechazando; por encima de 2⁵³ centavos un centavo de diferencia sigue siendo otro hash) y el hash de la versión anterior para la transición, vista de una orden (con `cancel_reason` siempre presente: el motivo en una `CANCELLED`, `null` en las demás), **guard de parsers**: `int8` y `numeric` llegan como string intacto, y escape de comodines en la búsqueda. |

| `test/unit/errors` | Los dos errores de tiempo de conexión de `pg-pool` (espera por una conexión libre y apertura de una nueva), que no traen código, → `503 TIMEOUT` con `Retry-After: 1`; con un código de Postgres, el mismo mensaje no se toma como timeout. |

Además: cancelación (200, 409, 404 de otro usuario), motivo de la cancelación ([#21](https://github.com/dante0x95/cocos-challenge/issues/21): la del usuario → `200` con `cancel_reason: "USER"` y el GET igual, mientras el replay del `POST` sigue devolviendo la respuesta original con `NEW`; | `test/bootstrap` | Base vacía → bootstrap → números de aceptación (753.000 / 125.500 / 627.500, posiciones, secuencias 1–7, cash en centavos, la API sin permisos de escritura). Segunda corrida: no aplica nada y la base queda idéntica. Una migración aplicada que cambió aborta. Una base que ya tiene las tablas del challenge no se vuelve a sembrar. Actualización desde la firma anterior de `app.place_order` (9 argumentos): después de aplicar las funciones dos veces queda solo la nueva, `api` la llama con 9 y 10 argumentos y una clave grabada antes da replay. Una base con el `SELECT` anterior de `api` sobre `app.users`: después de dos bootstraps queda revocado (`42501`) y `app.read_portfolio` sigue dando el portfolio y `APP06` para el rol `api`. Actualización a `cancel_reason` ([#21](https://github.com/dante0x95/cocos-challenge/issues/21)) desde una base sin la columna: las ya canceladas (la del challenge y una cancelada con la versión anterior) quedan `USER`, la migración corre una vez, `cancel_order_outcome` se reemplaza una sola vez (la segunda corrida no la vuelve a crear), `api` la llama y recibe el motivo, y una clave grabada antes devuelve exactamente su respuesta original (sin `cancel_reason`) sin otra orden. Un bootstrap que falla después de la migración no deja nada aplicado (ni la columna, ni `005` registrada, ni las funciones nuevas) y las anteriores siguen cancelando. Con conexiones reales y un lock como barrera a mitad del bootstrap: la migración ya corrió pero nadie la ve, y dos escritores que llaman la función anterior (uno esperando la barrera de despliegue, otro el lock de `app.orders`) fallan con `APP04` después del `COMMIT`, sin efectos; el reintento cancela con `USER`. La CLI (`node dist/db/bootstrap.js`, el `release_command` del deploy en Fly, [D-29](decisiones.md#d-29)) sale con 0 si el bootstrap pasa y con 1 si una migración falla, sin dejar nada aplicado. |

## Lo que no está cubierto

- El deploy en Fly: `release_command`, bluegreen y el workflow contra la app real. `test/unit/deploy-workflow` cubre la condición del workflow y el script del gate con un `curl` simulado; lo demás lo ensaya `deploy/fly/drills.sh` a mano, con la cuenta de Fly ([D-29](decisiones.md#d-29)).
- `docker compose up` de punta a punta: el CI construye la imagen y el bootstrap (`test/bootstrap`) cubre lo que corre el contenedor `migrate`, pero nadie levanta los contenedores.
- Rendimiento: se midió aparte, con el benchmark descripto en [`decision-snapshot.md`](decision-snapshot.md). No es parte de la suite.
